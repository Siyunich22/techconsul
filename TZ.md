## 0. Как пользоваться этим ТЗ (инструкция для Claude Code)

1. Положи в корень репозитория `TZ.md`, `CLAUDE.md`, `templates/tech_assessment_bank_v1.yaml`.
2. Работай **строго по фазам из раздела 12**. Не переходи к следующей фазе, пока не выполнены критерии приёмки текущей и не проходят тесты.
3. Источник истины о содержании отчёта — YAML-шаблон, а не код. Ни один пункт ТЗ банка не хардкодится в промптах или Python-коде: всё читается из шаблона.
4. При неясности — делай разумное допущение, фиксируй его в `docs/DECISIONS.md` и продолжай.

## 1. Цель и результат

**Цель.** Веб-платформа, в которой пользователь загружает документы инвестпроекта (БП, ТЭО/BFS, ПСД, финмодель, договоры, КП поставщиков и т.д.). Платформа формирует **отчёт об оценке технической проработанности и закупок** в формате DOCX/PDF, полностью соответствующий структуре и требованиям эталонного ТЗ банка (разделы 1–6, пункты 3.1–3.7, реестр рисков 4.1–4.5, выводы 5.1).

**Конечный результат для пользователя:** кнопка «Получить результат» → файл `Оценка_техпроработанности_<Проект>_<дата>.docx` (+ PDF), в котором:
- каждый пункт ТЗ раскрыт **или** явно помечен как нераскрытый с причиной, влиянием на выводы, допущениями и рекомендацией (п. 5.1.3 ТЗ);
- каждый вывод имеет аргументацию и ссылку на источник: документ + страница или URL (пп. 5.1.1, 6.2, 6.8);
- по всем 15 обязательным рискам (11 технических + 4 по закупкам) указаны вероятность (5 градаций), масштаб влияния (3 градации), обоснование и мероприятия по управлению (пп. 4.3–4.5);
- приложены матрица покрытия пунктов ТЗ, перечень исходных документов, список источников и резюме экспертов.

**Принцип «эксперт — автор».** ИИ готовит черновик, отчёт подписывает эксперт-Исполнитель. Платформа обязана: (а) не выпускать финальную версию без проверки каждого раздела экспертом; (б) хранить журнал правок ИИ и эксперта. Банк может признать отчёт формальным (п. 6.8, 6.10). Сырой ИИ-текст без экспертной верификации — главный риск продукта, и интерфейс должен его исключать.

## 4. Функциональные требования по экранам

### 4.1. Регистрация / вход
- Регистрация организации-Исполнителя (наименование, БИН, адрес) + первого пользователя-руководителя.
- Вход, восстановление пароля по email, приглашение экспертов по ссылке.

### 4.2. Личный кабинет
Разделы:
1. **Профиль**: ФИО, должность, контакты, смена пароля.
2. **Организация-Исполнитель**: реквизиты (подставляются в п. 2.1 отчёта), логотип и `reference.docx` для фирменного стиля.
3. **Эксперты** — реестр с полями для п. 3.1.2 ТЗ: ФИО, специализация, образование, опыт исследований, стаж, контакты, загрузка резюме (PDF/DOCX). Резюме автоматически прикладываются в приложение отчёта.
4. **Мои задачи**: разделы, назначенные мне на проверку, по всем проектам.
5. **Использование**: расход токенов/стоимость по проектам за период, лимит организации.
6. **Настройки**: язык отчёта (RU; KZ/EN — фаза 9), формат номеров страниц, шрифт по умолчанию.

### 4.3. Портфель проектов (главная страница после входа)
- **Вид «таблица»** и **вид «карточки»**, переключатель.
- Колонки: наименование, Заказчик, отрасль, регион, бюджет проекта (KZT), статус, % покрытия пунктов ТЗ, интегральный уровень риска, ответственный, дата обновления.
- Статусы проекта: `Черновик` → `Документы загружены` → `Анализ идёт` → `На проверке экспертов` → `Утверждён` → `Выпущен`; плюс `Архив`.
- Фильтры: статус, отрасль, регион, ответственный, уровень риска, период; поиск по наименованию/Заказчику.
- **Дашборд портфеля** (над таблицей): число проектов по статусам; суммарный бюджет; тепловая карта рисков по портфелю (вероятность × влияние, количество рисков в ячейке); топ-5 наиболее частых рисков; средний % покрытия ТЗ.
- Кнопка **«+ Новый проект»**.
- Экспорт портфеля в XLSX.

### 4.4. Создание проекта (мастер в 3 шага)
1. **Паспорт:** наименование проекта, Заказчик (ТОО/АО, БИН), отрасль (справочник ОКЭД-секций), регион/площадка, заявленная мощность, бюджет проекта, валюта, шаблон ТЗ (по умолчанию `tech_assessment_bank_v1`), банк-получатель отчёта.
2. **Независимость (п. 6.4 ТЗ):** чек-лист конфликта интересов: аффилированность Исполнителя с Заказчиком; участие в разработке БП/ТЭО; является ли Исполнитель поставщиком по проекту; опыт совместной деятельности (текст → п. 2.1 отчёта). При «да» на любой из первых трёх вопросов — красное предупреждение и обязательное поле «обоснование»; без него проект не выпускается.
3. **Команда:** руководитель + эксперты, закрепление экспертов за разделами 3.2–3.7, 4.

### 4.5. Карточка проекта — вкладки

**А. Документы** — **кнопка «Загрузить документы»**
- Drag-and-drop, множественная загрузка, папки и архивы (zip/rar/7z распаковываются). Форматы: pdf (в т.ч. скан), docx/doc, xlsx/xls/xlsm, pptx, jpg/png, dwg→только метаданные, dxf, msg/eml, txt/csv. Лимит 500 МБ на файл, 5 ГБ на проект.
- Автоклассификация по категориям п. 2.2 ТЗ: `договор_услуг`, `бизнес_план`, `тэо_bfs`, `псд`, `смета`, `финмодель`, `кп_поставщиков`, `договоры_поставки`, `техусловия`, `экология` (ОВОС, заключения), `правоустанавливающие` (земля, площадка), `закупочные_процедуры`, `прочее`. Пользователь может исправить категорию.
- Прогресс обработки по каждому файлу: загружен → распознан → проиндексирован; ошибки с причиной.
- **Индикатор полноты пакета:** какие ключевые документы отсутствуют (например, «Нет ПСД — пункты 3.4.2, 3.7.4 будут раскрыты частично»). Связь «документ → пункты ТЗ» берётся из `inputs` в YAML-шаблоне.
- Предпросмотр документа с подсветкой фрагмента при переходе по ссылке-источнику.

**Б. Паспорт проекта (извлечённые данные)**
Структурированная выжимка, которую ИИ извлекает из документов, а эксперт подтверждает до запуска анализа:
- площадка и инфраструктура (координаты/адрес, подъездные пути, ж/д, энергоисточники, ТУ);
- технология и продукция (продукт, мощность, производственная программа по годам);
- **перечень оборудования** (наименование, кол-во, характеристики, производитель, страна, стоимость, источник цены);
- сырьё и материалы (вид, поставщик, расстояние, объём, нормы расхода);
- энергоресурсы (электричество, газ, вода, тепло — нормы и источники);
- бюджет проекта (CAPEX по статьям, OPEX/maintenance capex, источники финансирования);
- график инвестиционной фазы;
- закупки (процедуры, поставщики, статус договоров);
- экология (класс опасности, источники выбросов, наличие ОВОС/заключений).
Каждое поле: значение, единица, источник (документ+страница), уверенность. Противоречия между документами (например, мощность в БП ≠ ТЭО) выводятся отдельным блоком **«Расхождения»** — они же идут в замечания отчёта.

**В. Оценка** — **кнопка «Запустить оценку»**
- Перед запуском: проверка полноты паспорта и предупреждение о стоимости (оценка токенов).
- Прогресс по разделам в реальном времени (SSE/WebSocket): 3.1 … 3.7, 4, 5.
- Возможность перезапустить отдельный пункт/раздел (**«Пересобрать раздел»**) с доп. инструкцией эксперта («учти КП от 15.09», «сравни с линиями Bühler»).

**Г. Разделы отчёта (проверка экспертом)**
- Дерево пунктов ТЗ слева, редактор TipTap справа.
- Для каждого пункта: статус раскрытия (`раскрыт` / `частично` / `не раскрыт`), текст, таблицы, перечень источников (кликабельно), замечания валидатора.
- Статус проверки: `черновик ИИ` → `на проверке` → `утверждён экспертом` (+ ФИО, дата). Diff между версией ИИ и экспертной.
- Комментарии в треде внутри пункта.

**Д. Риски**
- Реестр: 11 технических рисков (4.1) + 4 риска закупок (4.2) — обязательные и неудаляемые; можно добавлять доп. риски.
- По каждому: вероятность (Низкая / От низкой до умеренной / Умеренная / От умеренной до высокой / Высокая), масштаб влияния (Не значительный / Средний / Большой), **аргументированное обоснование** со ссылками, мероприятия по управлению/снижению/устранению, связанные пункты ТЗ.
- Тепловая карта 5×3 на экране и в отчёте.

**Е. Матрица покрытия** — таблица «пункт ТЗ → статус → источники → эксперт → утверждено». Отчёт не выпускается, пока все пункты не утверждены (раскрыт или обоснованно «не раскрыт»).

**Ж. Результат** — **кнопка «Получить результат»**
- Предпросмотр (HTML-рендер того же контента).
- «Скачать DOCX», «Скачать PDF», «Скачать пакет» (ZIP: отчёт + приложения + реестр рисков XLSX + перечень источников).
- Версионирование: v0.1 (черновик ИИ), v0.2…, v1.0 (выпущенная). Каждая версия неизменяема; при выпуске — водяной знак «Черновик» снимается, в колонтитул добавляется номер версии и хеш.

## 5. Конвейер обработки (backend pipeline)

```
upload → ingest → classify → index (RAG) → extract passport → [эксперт подтверждает паспорт]
       → analyze sections (параллельно по пунктам) → risk assessment → conclusions (5.1)
       → validate → [эксперты утверждают] → render DOCX/PDF
```

### 5.1. Ingest
- Для каждого файла: текст постранично с номерами страниц; таблицы — отдельно в структурированном виде (xlsx → листы/диапазоны; pdf-таблицы — через PyMuPDF `find_tables`); изображения/сканы — OCR; чертежи — метаданные + PNG превью.
- Финмодель (xlsx): извлечь значения ключевых листов (CAPEX, производство, сырьё, OPEX) с адресами ячеек как источником.
- Chunking ≈ 800–1200 токенов с перекрытием, метаданные `{doc_id, category, page, sheet, cell_range}`; эмбеддинги в pgvector.

### 5.2. Извлечение паспорта
- Sonnet с JSON-схемой паспорта (Pydantic → JSON Schema), map-reduce по документам, затем сведение и выявление расхождений.

### 5.3. Анализ пунктов ТЗ (ядро)
Для **каждого пункта** YAML-шаблона запускается задача-агент (Opus) со следующими инструментами (tool use):

| Инструмент | Назначение |
|---|---|
| `search_project_docs(query, categories?, k)` | гибридный поиск (BM25 + вектор) по документам проекта, возвращает фрагменты с `doc_id/page` |
| `get_passport(section)` | подтверждённые данные паспорта |
| `search_reference_library(query)` | поиск по справочной библиотеке платформы: справочники НДТ РК, Экологический кодекс РК, КоАП РК (экологические штрафы), СН/СП РК, отраслевые стандарты |
| `web_search` / `web_fetch` (server tools Anthropic) | мировые технологии, аналоги оборудования (≥3 альтернативы по п. 3.4.1), референс-проекты (3.3.4), цены, патенты |
| `calc(python_expression)` | изолированные расчёты: удельные капзатраты на единицу продукции, материальный баланс, загрузка оборудования, нормы расхода |

Выход агента — строго по схеме `SectionResult`:
```json
{
  "item_id": "3.4.1",
  "disclosure_status": "full | partial | not_disclosed",
  "summary": "краткий вывод 1–3 предложения",
  "analysis_md": "развёрнутый текст с аргументацией",
  "tables": [{"title": "...", "columns": [...], "rows": [[...]]}],
  "findings": [{"text": "...", "source_ids": ["S12"]}],
  "remarks": ["замечание"],
  "recommendations": ["рекомендация"],
  "gap": {"reason": "...", "impact_on_conclusions": "...", "assumptions": "...", "recommendation": "..."},
  "sources": [{"id": "S12", "type": "doc|web|reference", "doc_id": "...", "page": 14, "url": null, "title": "...", "accessed_at": "..."}],
  "confidence": 0.0
}
```
Правила для агентов (в системный промпт, из `CLAUDE.md` → `prompts/`):
- Ни одного утверждения о проекте без `source_ids`. Внешние данные — только из официальных, авторитетных, независимых и актуальных источников (п. 6.2); каждый URL с датой обращения.
- Если данных нет — `disclosure_status = not_disclosed` и обязательно заполненный `gap` (п. 5.1.3, 6.1): суть недостатка, проблематика, оптимальный вариант для проекта.
- Запрет «воды»: не включать общую информацию без вывода, напрямую относящегося к проекту (п. 6.10).
- Однозначные формулировки (п. 5.1.2): без «возможно», «вероятно», если нет количественной оценки.
- Пункты-«выводы» и «замечания/рекомендации» (3.3.5–3.3.6, 3.4.12–3.4.13, 3.5.6–3.5.7, 3.7.6–3.7.7) запускаются **после** аналитических пунктов своего раздела и получают их результаты на вход (зависимости `depends_on` в YAML).

### 5.4. Оценка рисков
- После разделов 3.x: агент оценивает 15 обязательных рисков + предлагает дополнительные, используя результаты разделов; на выходе `RiskItem {code, title, probability(1–5), impact(1–3), rationale_md, source_ids, mitigation[], related_items[]}`.
- Интегральный уровень риска проекта: детерминированная формула в коде (не LLM), например максимум + доля рисков в красной зоне; правило зон хранится в YAML.

### 5.5. Выводы (раздел 5.1)
- Агент формирует выводы на основе утверждённых разделов и рисков: достаточность проработки документации по частям, обоснованность заявленной стоимости (бюджета), возможность реализации, перечень нераскрытых пунктов с анализом их влияния.

### 5.6. Валидатор (детерминированный + LLM-ревью)
Детерминированные проверки (блокирующие выпуск):
- все пункты шаблона присутствуют; у каждого `full/partial` — ≥1 источник; у каждого `not_disclosed` — заполнены 4 поля `gap`;
- по 3.4.1 — для каждой единицы основного оборудования ≥3 альтернативы в таблице сравнения;
- все 15 обязательных рисков оценены по обеим шкалам, есть обоснование и мероприятия;
- все источники-документы существуют, страницы в пределах документа; web-источники с URL и датой;
- все разделы утверждены экспертом;
- заполнен блок независимости (п. 2.1, 6.4).
LLM-ревью (неблокирующее, предупреждения): выводы без аргументов, двусмысленные формулировки, противоречия между разделами (например, мощность в 3.3 ≠ 3.4.5), избыточная информация.

### 5.7. Сборка документа
- `docxtpl`-шаблон `report_templates/tech_assessment_bank_v1.docx`, стили из `reference.docx` организации.
- Структура итогового документа:
  1. Титульный лист (наименование проекта, Заказчик, Исполнитель, дата, версия).
  2. Оглавление (поле TOC, обновляется при открытии; PDF — через LibreOffice с обновлением полей).
  3. Раздел 1 «Структура изложения материала».
  4. Раздел 2 «Общие данные»: 2.1 Заказчик и Исполнитель, аффилированность, опыт совместной деятельности; 2.2 перечень исходных документов (таблица: №, документ, категория, дата, кол-во стр.).
  5. Раздел 3 «Предмет оценки» с подразделами 3.1–3.7 по шаблону: для каждого пункта — заголовок-формулировка требования, анализ, таблицы, выводы, замечания/рекомендации; сноски/ссылки `[S12]` на источники.
  6. Раздел 4 «Проектные риски»: таблица реестра (№, риск, вероятность, влияние, обоснование, мероприятия) + тепловая карта (PNG через matplotlib, вставка в docx).
  7. Раздел 5 «Выводы».
  8. Раздел 6 — подтверждение соответствия требованиям к качеству (краткая декларация независимости и принципов).
  9. Приложения: А — список источников; Б — матрица покрытия пунктов ТЗ; В — резюме экспертов; Г — сравнительные таблицы оборудования (если громоздкие); Д — реестр рисков XLSX (в пакете).
- Нумерация разделов и пунктов — **как в шаблоне банка** (включая отсутствующий 3.6, см. раздел 13).

## 9. Нефункциональные требования

- **Конфиденциальность:** документы проектов — коммерческая тайна. Шифрование at rest (MinIO SSE) и in transit (TLS). В админке — явная отметка, что тексты отправляются в Anthropic API; переключатель «запретить web-поиск с отправкой названий проекта/Заказчика» (в поисковые запросы не подставлять наименования Заказчика).
- **Стоимость:** prompt caching контекста проекта (паспорт + перечень документов); оценка стоимости до запуска; месячный лимит организации; учёт токенов по каждому вызову.
- **Производительность:** проект 50 документов / 2 000 страниц — ingest ≤ 15 мин; полный анализ ≤ 40 мин (параллельно по пунктам, ограничение конкуррентности настраивается); генерация DOCX ≤ 1 мин.
- **Надёжность:** идемпотентные задачи Celery, ретраи LLM с экспоненциальной паузой, частичный результат сохраняется по пунктам (падение одного пункта не валит прогон).
- **Аудит:** все действия (загрузка, запуск, правка, утверждение, выпуск) — в AuditLog.
- **Язык интерфейса:** русский; i18n-ключи заложить сразу (next-intl).
- **Доступность:** работа в последних Chrome/Edge/Safari; адаптив до планшета (портфель и чтение отчёта — до телефона).

## 13. Замечания к эталонному ТЗ банка (учесть в реализации)

1. **Пропущен раздел 3.6** — нумерация идёт 3.5 → 3.7. Платформа сохраняет нумерацию эталона (банк сверяет по ней). В YAML есть необязательный пункт `3.6` (`enabled: false`). Предлагаю по умолчанию трактовать его как «Оценка проработки закупок и стоимости проекта»: предмет оценки (раздел 3) прямо называет закупки и бюджет, а отдельного аналитического раздела по ним в эталоне нет — есть только риски 4.2. Включается флагом на уровне проекта.
2. **Раздел 3.2** в заголовке упоминает энергетическую и социальную инфраструктуру, но содержит только пункт о транспорте. В YAML добавлены пункты `3.2.2` (энергетика/инженерные сети) и `3.2.3` (социальная инфраструктура и трудовые ресурсы) с пометкой `extension: true`. Пункт 5.1.6 эталона прямо допускает такие дополнения. В отчёте они идут после обязательного пункта и маркируются как дополнительные.
3. **П. 6.2** обрывается на фразе «Также должна быть представлена». Трактуем как требование приложить подтверждающие материалы (п. 5.1.5) и фиксируем это в `docs/DECISIONS.md`.
4. **НДТ (3.4.8)** требует актуальных справочников НДТ РК в справочной библиотеке. Без них пункт будет «частично раскрыт». Загрузка справочников администратором входит в фазу 2.
