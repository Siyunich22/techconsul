# Решения и допущения

Формат: дата — решение — причина.

## 2026-10-01 — Фаза 0

- **D-001. Синхронный SQLAlchemy 2 + psycopg 3 (`postgresql+psycopg://`).**
  Один драйвер для API и Celery-воркеров; FastAPI выполняет sync-эндпоинты в threadpool. psycopg 3 поддерживает и async — переход возможен без смены драйвера, если упрёмся в I/O.

- **D-002. Браузер обращается только к своему origin; Next.js проксирует `/api/*` на FastAPI (rewrites).**
  Нет CORS, JWT в httpOnly-cookie остаётся first-party (TZ §3). Для prod-сборки адрес API задаётся на этапе build (`API_INTERNAL_URL`).

- **D-003. `/health` проверяет Postgres (включая наличие расширения `vector`), Redis и бакет MinIO; 200/`ok` или 503/`degraded`.**
  Критерий фазы 0 «/health = ok» тогда означает реально поднятый стек, а не только живой процесс. Дублируется как `/api/v1/health` для фронтенда.
  Проверки идут параллельно с общим дедлайном `HEALTH_CHECK_TIMEOUT_S` (3 с) + `connect_timeout` у Postgres: на Windows недоступный хост мог подвешивать запрос на минуты.

- **D-004. Миграции применяются при старте контейнера `api` (`alembic upgrade head`), плюс `make migrate`.**
  Для dev-окружения это упрощает `make up`. В prod — отдельный шаг деплоя (пересмотреть перед продом).

- **D-005. Бакет MinIO создаётся одноразовым сервисом `minio-init` с включённым версионированием.**
  Реализует «версии файлов не перезаписываются» (TZ §3, CLAUDE.md п.8) на уровне хранилища; приложение дополнительно использует уникальные ключи.

- **D-006. Tailwind v4 (CSS-first, без `tailwind.config`), компоненты shadcn/ui (стиль new-york) добавляются в `components/ui`.**
  Актуальная связка для Next.js 15; `components.json` позволяет добавлять компоненты через `npx shadcn add`.

- **D-007. next-intl без локали в URL; единственная локаль `ru`, ключи в `frontend/messages/ru.json`.**
  TZ §9 требует заложить i18n сразу; KZ/EN — фаза 9 (выбор локали через cookie/настройки пользователя).

- **D-008. Node.js 24 LTS (локально и в образе frontend).**
  Актуальная LTS на 10.2026; Node 20 вышел из поддержки в апреле 2026.

- **D-009. Тесты по маркерам: `integration` (нужен поднятый стек, `RUN_INTEGRATION=1`), `live` (реальный Anthropic API, `RUN_LIVE_LLM=1`).**
  `make test` проходит без сервисов (CI), `make test-integration` проверяет живое окружение.

- **D-010. Для Windows без `make` добавлен `make.ps1` с теми же целями.**
  Основная машина разработки — Windows; `Makefile` остаётся каноническим для Linux/WSL/CI.

## 2026-10-02 — Фаза 0 (запуск стека)

- **D-011. Локальный MinIO — образ `bitnamilegacy/minio:2025.5.24` вместо `minio/minio`.**
  Официальные образы MinIO сняты с Docker Hub и quay.io (pull access denied). Bitnami-образ — тот же сервер MinIO (versioning, SSE, `mc` внутри), но заморожен и без обновлений безопасности → только для dev. Код работает с хранилищем через boto3 (S3 API), поэтому в проде подходит любое S3-совместимое хранилище; альтернатива для dev, если образ исчезнет, — SeaweedFS.

- **D-012. `make.ps1` сохраняется в UTF-8 с BOM (`.editorconfig`), `$ErrorActionPreference = "Continue"`.**
  Windows PowerShell 5.1 читает .ps1 без BOM как ANSI (ломает кириллицу) и при перенаправлении считает stderr нативных команд ошибкой; успех определяется по `$LASTEXITCODE`.

## 2026-10-02 — Фаза 1

- **D-013. Роли: `admin` (платформа), `manager` (руководитель-Исполнитель), `expert`, `observer`.** Регистрация создаёт организацию и руководителя; остальные — по приглашению. Эксперт видит только проекты, где он в команде; наблюдатель — пока ничего (фаза 9).
- **D-014. JWT: access 15 мин (cookie `to_access`, Path=/), refresh 14 дней (cookie `to_refresh`, Path=/api/v1/auth), оба httpOnly + SameSite=Lax.** Refresh-сессии хранятся в БД (`refresh_sessions`, id = jti), ротация при каждом refresh; повтор отозванного токена отзывает все сессии пользователя. Защита маршрутов на frontend — на клиенте (AppShell → `/me`, при 401 — тихий refresh), т.к. refresh-cookie не видна middleware.
- **D-015. Токены сброса пароля и приглашений — случайные, в БД хранится SHA-256; одноразовые; TTL 2 ч / 7 дней.** `/auth/forgot` всегда отвечает 204 (не раскрываем наличие email). Ссылка-приглашение дополнительно возвращается руководителю в ответе API — на случай, если письмо не дошло. В dev письма перехватывает Mailpit (`:8025`).
- **D-016. Команда проекта ссылается на запись реестра экспертов (`ProjectMember.expert_id`), а не на пользователя.** Эксперт для п. 3.1.2 и резюме (прил. В) может не иметь учётной записи; доступ к платформе даёт привязка `Expert.user_id` через приглашение. Отклонение от модели TZ §6 (`ProjectMember.user_id`).
- **D-017. Разделы для закрепления за экспертами вычисляются из YAML:** все подразделы и аналитические разделы верхнего уровня без подразделов (`kind` ≠ info) → 3.1…3.7, 4, 5. Необязательные (`enabled: false`, например 3.6) доступны, только если включены в `Project.enabled_optional_items`.
- **D-018. Блок независимости можно сохранить неполным;** `is_complete` = ответы на 3 вопроса + обоснование при «да». Мастер требует ответить на вопросы, а выпуск отчёта блокирует валидатор (фаза 7) — «без обоснования проект не выпускается» (TZ §4.4).
- **D-019. Удаляется только черновик; остальные проекты — в архив (с восстановлением прежнего статуса).** Эксперта, включённого в команду, удалить нельзя — только деактивировать.
- **D-020. Изоляция: все tenant-выборки через `services/tenancy.py` (`scoped`, `get_scoped`); чужой объект → 404.** Тесты: `tests/api/test_isolation.py` (API-утечки) + структурный тест «у каждой tenant-таблицы есть org_id».
- **D-021. Backend-тесты — на реальном Postgres:** тестовая БД `<db>_test` пересоздаётся на сессию, миграции применяются Alembic, каждый тест в транзакции с откатом; S3 и почта — фейки. Приложение в тестах всегда работает через тестовую сессию (ошибка с записью в dev-БД исправлена).
- **D-022. e2e гоняются против production-сборки frontend (Playwright `webServer`, порт 3100) и API из стека.** Dev-сервер Next с HMR перезагружал страницы при первой компиляции маршрута и терял ввод. Маркер `body[data-hydrated]` — тесты ждут гидратацию.
- **D-023. Риск-фильтр портфеля, дашборд и экспорт XLSX — в фазах 6/9:** уровни интегрального риска задаются правилом зон в YAML (фаза 6).

## 2026-10-02 — Фаза 2

- **D-024. Загрузка частями напрямую в S3 multipart через API** (`/uploads` → `PUT …/parts/{n}` → `complete`). Части по 8 МБ (≥5 МБ — минимум S3), 3 части и 3 файла параллельно, повтор части при 5xx. Временных файлов на API нет; лимиты 500 МБ/файл и 5 ГБ/проект проверяются при `init` (с учётом незавершённых загрузок).
- **D-025. Архивы и письма — контейнеры:** распаковываются в дочерние документы (`parent_id`, путь `архив.zip/папка/файл`), сам контейнер получает статус `extracted`. zip — stdlib с исправлением имён cp866 (архиваторы Windows) и защитой от path traversal и zip-бомб (лимиты числа файлов и объёма); rar/7z — `unar` (свободный, читает RAR). Вложения eml/msg — тоже дочерние документы.
- **D-026. Офисные форматы (docx/doc/rtf/odt/pptx/ppt) конвертируются LibreOffice в PDF;** страницы и превью берутся из PDF. Это даёт номера страниц для ссылок «документ + страница» и единый предпросмотр с подсветкой. PDF-версия хранится как `preview_key`; таблицы docx берутся из самого docx (точнее). Отдельный профиль LibreOffice на вызов — параллельные воркеры не конфликтуют.
- **D-027. Excel: лист = «страница», строки с номерами `[r]`, чанки с диапазоном ячеек `A1:H40`** (источник «лист + ячейки»). Формулы без сохранённых значений (книга не пересчитана в Excel) → пересчёт через LibreOffice; определяется по доле пустых значений у формул.
- **D-028. OCR — Tesseract rus+kaz+eng для изображений и страниц PDF с <40 символами текста** (рендер 300 dpi, мелкие изображения масштабируются до ~2000 px).
- **D-029. Два воркера Celery:** `worker` (очереди ingest, default; разбор, OCR, LibreOffice; параллельно) и `worker-index` (очередь index; эмбеддинги; concurrency 1 — модель e5-large ~2 ГБ в памяти один раз). API загружает модель лениво для эмбеддинга поисковых запросов. Справочники обрабатываются целиком в очереди index. У api и воркеров один образ `techocenka-backend:dev`.
- **D-030. Эмбеддинги — fastembed (ONNX) с `intfloat/multilingual-e5-large`, 1024 измерения, явные префиксы `passage:`/`query:`.** Без torch — образ легче. Модель кэшируется в томе `models`. Размерность зашита в колонку `chunks.embedding` — смена модели требует миграции. В тестах — детерминированный `HashEmbedder` той же размерности.
- **D-031. Гибридный поиск:** `tsvector` (конфигурация `russian`, вычисляемая колонка + GIN) и косинус по HNSW-индексу, слияние Reciprocal Rank Fusion (k=60); всегда с фильтром `org_id` + `project_id`.
- **D-032. Токены для чанкинга оцениваются как `len(text)/3.2`** (русский текст), без вызова токенизатора; цель 1000 токенов, перекрытие 150.
- **D-033. Классификация: правила (`pipeline/classification.yaml` — имя файла, фразы в тексте, названия листов) → при уверенности < 0.6 Haiku со структурированным выводом.** Набор категорий — из шаблона ТЗ проекта; правила для отсутствующих в шаблоне категорий игнорируются. Без ключа API или при ошибке LLM остаётся результат правил. Ручная категория (`category_source = user`) не перезаписывается при повторной обработке.
- **D-034. LLM-клиент:** `messages.parse` с Pydantic-схемой (`output_format`), системный промпт с `cache_control`, ретраи сети/429/5xx — в SDK (`max_retries=4`), невалидный ответ — 1 повтор с ошибкой в контексте, отказ (`stop_reason=refusal`) — без повтора. Каждый вызов (и ошибка) пишется в `llm_calls` с токенами и стоимостью (прайс в `llm/cost.py`). Промпты — `llm/prompts/*.md` с `$переменными`. Server-side fallbacks для Opus/Sonnet добавим в фазе 5 (там первые вызовы этих моделей).
- **D-035. Удаление документа — мягкое** (`deleted_at`, вместе с вложенными); чанки удаляются из индекса, файл в хранилище остаётся (неизменяемость, аудит). Удаляет только руководитель; загружать и править категорию может и эксперт команды.
- **D-036. Полнота пакета:** для каждого пункта шаблона с `inputs` — `full`/`partial`/`none` по наличию распознанных документов нужных категорий; недостающие категории → «пункты X будут раскрыты частично» или «не останется исходных документов». `requires_reference` сверяется со справочной библиотекой (проиндексированные документы нужного типа).
- **D-037. Справочная библиотека — глобальная** (`reference_docs`, `reference_chunks` без `org_id`), ведёт администратор платформы (`role=admin`, создаётся `python -m app.cli create-admin` / `make seed`). Тексты справочников, как и документов проектов, уходят в Anthropic при анализе — это отмечено в админке.
- **D-039. Модель эмбеддингов раскладывается в «плоский» каталог (`/models/flat/…`) через `snapshot_download(local_dir=…)`.** onnxruntime 1.30 отказывается грузить внешние веса `model.onnx_data` по символическим ссылкам кэша Hugging Face («External data path escapes model directory») — ошибка проявилась только на живом стеке.
- **D-040. ⚠ Производительность индекса не укладывается в TZ §9 с e5-large на CPU.** Замер в контейнере (8 vCPU): 1,3 с на чанк; 2 000 страниц ≈ 1 500 чанков ≈ 33 мин только на эмбеддинги (цель — ingest ≤ 15 мин). Разбор и OCR укладываются (параллельно, секунды на файл). Варианты: GPU/больше ядер для `worker-index`; модель `Qwen/Qwen3-Embedding-0.6B-Q` (квантованная, та же размерность 1024 — переключение настройкой `EMBEDDING_MODEL` без миграции, качество и скорость нужно замерить) или `google/embeddinggemma-300m` (768 — нужна миграция). По умолчанию оставлена модель из ТЗ; решение — за заказчиком платформы. Полный прогон на 50 документах / 2 000 страниц не выполнялся — оценка по замеру.
- **D-041. e5-large усекает вход до 512 токенов,** а чанки по ТЗ — 800–1 200 токенов: в вектор попадает начало чанка, остальное находит полнотекстовая часть гибридного поиска. Уменьшение чанков до 512 удвоит их число и время индексации — не делаем до решения по D-040.
- **D-038. Прогресс обработки на фронтенде — опрос `GET /documents` раз в 2 с, пока есть файлы в обработке.** SSE появится для прогона оценки в фазе 5.

## 2026-10-02 — Фаза 3

- **D-042. Проверка шаблона в два слоя:** JSON-схема (`template_engine/schema.json`, Draft 2020-12, `additionalProperties: false` везде — опечатки в полях ловятся) + семантика в коде: уникальность id и префикс родителя, `inputs` ⊂ `document_categories`, `expert_role` ⊂ `expert_roles`, ссылки `depends_on`/`related` (включая маски `3.4.*`) указывают на существующие пункты, отсутствие циклов зависимостей, шкалы рисков подряд с 1, уникальные коды обязательных рисков, синтаксис выражений зон. Ошибки блокируют загрузку, предупреждения сохраняются у версии (`warnings_json`) и показываются администратору.
- **D-043. Ссылки на пункты выключенных по умолчанию разделов — предупреждение, не ошибка.** ⚠ Приложенный шаблон даёт 5 таких предупреждений: обязательные риски T10, P1, P3, P4 (и частично P2) связаны только с разделом 3.6 (`enabled: false`). Без включения 3.6 у этих рисков нет аналитической опоры в разделах 3.x — агент рисков (фаза 6) будет опираться на документы и 3.4.1/3.4.2. Рекомендация: включать 3.6 по умолчанию для проектов с закупками.
- **D-044. Выражения зон риска (`p*i >= 10 or …`) вычисляются безопасным интерпретатором** (`template_engine/expr.py`): разбор `ast` с белым списком (переменные `p`, `i`, числа, арифметика, сравнения, and/or/not), без `eval`. Зоны проверяются по порядку red → yellow → green.
- **D-045. Версии шаблонов неизменяемы:** новая версия — новый `code` (повтор кода → 409). Проект фиксирует `template_version_id` при создании; смена шаблона по умолчанию влияет только на новые проекты. Удалить можно только неиспользуемую и не дефолтную версию.
- **D-046. Дерево пунктов (`template_engine/tree.py`) раскрывает маски `depends_on` в конкретные id пунктов** и учитывает включённые проектом необязательные разделы (`enabled`). Используется UI («Разделы отчёта» — только чтение до фазы 7), а дальше — оркестратором анализа, валидатором и рендером.
- **D-047. Правило валидатора `min_alternatives_3_4_1` реализуется по данным:** проверяются пункты с `output_hints.min_alternatives`, а не захардкоженный id 3.4.1 (имя правила оставлено как в шаблоне).
- **D-048. В dev uvicorn перезагружается опросом файлов (`WATCHFILES_FORCE_POLLING`)** — события inotify с томов Windows не доходят, API продолжал работать на старом коде.
- **D-049. Сравнение с `Qwen3-Embedding-0.6B-Q` (D-040) не выполнено:** модель не скачивается с CDN Hugging Face из этой сети (ошибка xet/CAS, в том числе с `HF_HUB_DISABLE_XET=1`). Замер e5-large на 12 запросах к sample_project, только векторная часть: top-1 6/12, top-3 8/12; в рабочем поиске добавляется полнотекстовая часть.

## 2026-10-06 — Подготовка к деплою на Railway

- **D-050. Образ backend собирается из корня репозитория** (`backend/Dockerfile`, корневой `.dockerignore`): в образ копируются шаблоны ТЗ из `templates/` — раньше они только монтировались томом в compose, и на платформе API не нашёл бы шаблон по умолчанию.
- **D-051. Эмбеддинг поискового запроса считает `worker-index`** (задача `index.embed_query`, очередь `index`, `QUERY_EMBEDDING_MODE=worker`). Модель ~2 ГБ живёт в одном сервисе с томом `/models`; API не грузит её в память и не скачивает при каждом деплое. Первый запрос после рестарта воркера ~15 с (загрузка модели), дальше — доли секунды.
- **D-052. Совместимость с PaaS:** `postgres://`/`postgresql://` из `DATABASE_URL` приводится к `postgresql+psycopg://`; API слушает `::` (IPv4+IPv6 — приватная сеть Railway) на `$PORT`; бакет S3 создаётся при старте API (`S3_AUTO_CREATE_BUCKET`), отдельный init-сервис не нужен; миграции — `preDeployCommand` сервиса `api`. Конфиги — `backend/railway.{api,worker,worker-index}.json`, `frontend/railway.json`; инструкция — `docs/DEPLOY_RAILWAY.md`.
- **D-053. Концы строк — LF (`.gitattributes`), кроме `.ps1`.** 37 файлов попали в git с CRLF из-за правок скриптами на Windows; для Linux-контейнеров (Makefile, shell) это опасно.

## 2026-10-13 — Деплой на Railway: исправления

- **D-054. API слушает пустой host (`--host ''`), а не `::`.** Уточнение D-052: с `::` uvicorn слушает только IPv6 (asyncio ставит `IPV6_V6ONLY`), запросы по IPv4 получали «connection refused» — healthcheck `/health` не проходил. Проверено локальной сборкой образов и запуском стека в режиме Railway (`postgres://`, `APP_ENV=staging`, `alembic upgrade head`, оба воркера, прокси `web → api`).
- **D-055. Для `web` путь к конфигу указывается явно (`/frontend/railway.json`).** Railway не ищет файл конфига относительно Root Directory: без явного пути сервис может взять корневой `railway.json` (конфиг `api`, `backend/Dockerfile`) и не собраться.

## 2026-10-23 — Фаза 4: паспорт проекта

- **D-056. Схема паспорта — Pydantic (`app/schemas/passport.py`), а не YAML шаблона.** Паспорт не входит в структуру отчёта банка (TZ §5.2: «Pydantic → JSON Schema»); подписи разделов, полей и колонок берутся из схемы и отдаются фронтенду (`GET /passport/layout`), без дублирования во фронтенде.
- **D-057. Источник поля — метка страницы `P1…Pn`, а не id документа от модели.** Извлечение раздаёт метки страницам/листам готовых документов, модель ссылается на них, код превращает метку в «документ + страница/лист». Поле, строка таблицы или расхождение без существующей метки отбрасываются (правило 2). Значение без источника допустимо только с пометкой `manual` (ввёл эксперт).
- **D-058. Map-reduce:** пакеты страниц до 60 000 символов, 4 параллельных вызова Sonnet; при одной части сведение не вызывается (экономия); если сведение через ИИ не удалось — запасное слияние без ИИ (наибольшая уверенность, объединение таблиц) и предупреждение. Сбой части — предупреждение, не ошибка прогона. Повторный запуск идемпотентен по `run_id`; «извлекается» дольше 60 мин — считается зависшим, можно перезапустить.
- **D-059. Паспорт извлекают, правят и подтверждают руководитель и эксперты проекта.** Любая правка после подтверждения снимает подтверждение. Расхождения подтверждение не блокируют — они идут в замечания отчёта, эксперт фиксирует принятое решение в `resolution`.
- **D-060. Live-приёмка на sample_project** — сначала не выполнялась (не было `ANTHROPIC_API_KEY`), выполнена 2026-11-02 после D-065. Тест `test_live_sample_project_passport` (`RUN_LIVE_LLM=1`) готов; конвейер проверен мок-моделью (источники со страницами, отброс выдуманных меток, расхождение мощности 300/320 т/сут).

## 2026-11-02 — Технические долги перед фазой 5

- **D-061. Railway: настройки сборки и запуска — в настройках сервисов, файлы `railway.json` удалены.** Config as Code Railway отключает с 2026-12-01; `railway config migrate status` показал, что сервисы стенда уже не читают эти файлы (параметры заданы через API при настройке). Переход на `.railway/railway.ts` не делаем: черновик миграции из старых файлов создавал бы лишние сервисы-дубликаты. Таблица настроек — `docs/DEPLOY_RAILWAY.md`.
- **D-062. Верхние границы версий зависимостей backend** (проверенный major). Пересборка образа без границ поставила `anthropic` 2.x и `pymupdf` 2.0: второй по-другому находит таблицы в PDF (теряет пробел в «12 500»), первый не проверялся с нашим клиентом LLM, а тесты используют мок-модель и такую поломку не видят.
- **D-063. Офисные документы: если прямой экспорт в PDF падает, конвертация через ODF** (`docx → odt → pdf`, `pptx → odp → pdf`). LibreOffice 25.2 падает на docx с надстройкой Office (`word/webextensions`) — документ попадал в индекс одной страницей без предпросмотра.
- **D-064. docker compose: образ backend собирает только `api`**, воркеры берут готовый тег (`pull_policy: never`). Три параллельные сборки одного тега зависали.
- **D-065. Паспорт извлекается без грамматики structured outputs.** Для схемы паспорта API отвечает «compiled grammar is too large» / «Schema is too complex» (лимит — около трёх разделов паспорта при всех обязательных полях). Вместо дробления на 3–4 вызова на пакет — `structured(..., constrained=False)`: JSON Schema в системном промпте (кэшируется), JSON из текста ответа проверяется Pydantic, при ошибке — один повтор с ошибкой (правило 7). Повтор — новым сообщением пользователя с прошлым ответом, без правки истории (preserved thinking). Мок-модель такие отказы API не ловит — нужен live-тест на каждую новую схему.
- **D-066. Ответы без грамматики (constrained=False) — потоком, лимиты паспорта: map 32k, reduce 64k токенов.** На реальном пакете (58 позиций оборудования, десятки строк сырья и финансирования) сведение упёрлось в 16k и ушло в запасное слияние без поиска расхождений.

- **D-069. Источники раздаёт код:** реестр прогона S1…Sn общий для всех пунктов (один фрагмент — одна метка); инструменты отдают фрагменты с метками, агент только ссылается. - **D-074. Оценка стоимости до запуска — по константам $0,15–0,80 за пункт ИИ** (уточнить по фактическим прогонам из `llm_calls.run_id`). ### Аудит 2026-11-02 (ошибки и безопасность; регрессия — `tests/api/test_audit_fixes.py`)

- **D-075. Прогоном занимается один процесс — advisory-блокировка Postgres по `run_id`** на отдельном соединении. Вторая доставка задачи Celery и задача пересборки при занятой блокировке завершаются; держатель после партии подбирает новые `pending`. Под блокировкой пункты в `running` — след упавшего воркера, сбрасываются в `pending`. Так исключены двойное выполнение (и двойная оплата) и расхождение S-меток между процессами (метка указывала бы на чужой документ). Сбой оркестратора помечает прогон `failed`, а не оставляет `running`. «Прогон жив» при новом запуске — по блокировке, по времени — только для стоящего в очереди. Пересборка ставится без `only`.
- **D-076. Ссылки пункта — только на метки, выданные ему инструментами, и источники его зависимостей** (не на весь реестр прогона). Висячие `[Wn]` удаляются; веб-источник — только http(s).
- **D-077. Celery: `visibility_timeout` 6 ч** (по умолчанию 1 ч — меньше прогона оценки, задача выдавалась второму воркеру), мягкие/жёсткие лимиты времени задач (оценка 5 ч, ingest 2 ч). Очереди — D-086.
- **D-078. Загрузка частей — атомарное слияние `parts_json` в JSONB** (параллельные части затирали друг друга: файлы > 8 МБ не завершались), тело части — с ограничением размера и вне цикла событий; `complete` — под блокировкой строки. Клиент обновляет сессию при 401 посреди длинной загрузки.
- **D-079. Архивы rar/7z: оглавление `lsar` до распаковки** — ссылки запрещены (симлинк на `/proc/self/environ` отдавал секреты воркера как документ), лимиты файлов и объёма по заявленным размерам; вложенность архивов ≤ 3; повторная обработка не дублирует вложения; документ в `processing` дольше 3 ч можно переобработать.
- **D-080. Аутентификация:** повторное приглашение гасит прежние ссылки, принятое приглашение нельзя использовать снова (руководитель не может войти под экспертом); смена пароля/приглашение/сброс отзывают сессии; лимиты частоты (Redis) на вход (10 / 15 мин на учётную запись, 100 на адрес), сброс пароля, регистрацию, токены; одинаковое время ответа для неизвестного email; БИН платформы `000000000000` не регистрируется.
- **D-081. Роли:** эксперт пересобирает только пункты своих разделов (`assigned_items`; руководитель команды — любые); наблюдатель не видит реестр экспертов, резюме и reference.docx.
- **D-082. Заголовки:** `nosniff` на всех ответах, CSP `sandbox` для SVG/HTML (SVG-логотип со скриптом). Вне `dev` API не стартует без `COOKIE_SECURE=true`, любой процесс — с S3-секретом по умолчанию.
- **D-083. Сохранение профиля организации сливает настройки**, а не заменяет: форма без поля не возвращает веб-поиск во «включён» (конфиденциальность, TZ §9); переключатель веб-поиска — в профиле организации.
- **D-084. LLM-клиент:** обрыв потока (`overloaded_error` посреди ответа) — 2 повтора с паузой; обрезанный ход агента не остаётся в истории; кэш-точка на конце истории агента; `web_fetch` ≤ 20 000 токенов на страницу; веб-поиск ($10 / 1000) учитывается в стоимости; итоговый JSON — последний полный объект, прошедший схему. `calc`: аргументы и результаты ограничены (`round(1, -10**9)` вешал воркер). Поиск: итеративное HNSW-сканирование (pgvector 0.8) — фильтр проекта больше не обнуляет векторную часть. Паспорт: любой сбой → «Ошибка», не вечное «Извлечение».

- **D-085. Повторное извлечение паспорта сохраняет работу эксперта:** поля и строки `manual` переносятся поверх ответа ИИ (метки P-n сопоставляются по документу и странице/листу), комментарии к расхождениям — по полю; `ai_data_json` — чистый ответ ИИ. Строка паспорта блокируется при правке, подтверждении, запуске и записи результата.
- **D-086. Очереди:** `llm` (паспорт, оценка) — отдельный процесс Celery в контейнере `worker`, слоты загрузки документов не занимает; `query` (эмбеддинг поискового запроса) — в `worker-index`, который теперь работает потоками (`--pool threads`, 3): модель в памяти одна, одновременно идёт одна индексация (занято — задача возвращается в очередь), остальные потоки отвечают на запросы. Запуск — `workers/start.sh worker|index`.
- **D-087. Контейнеры — от пользователя `app`** (entrypoint отдаёт ему том моделей и сбрасывает права через `setpriv`); тестовые зависимости — только в локальной сборке (`INSTALL_DEV=1`). LibreOffice — с профилем без сети (ручной прокси на 127.0.0.1:9), без макросов и активного содержимого, с окружением без секретов; по таймауту завершается вся группа процессов. Проверено: `WEBSERVICE` к локальному серверу не обращается.
- **D-088. CSRF — проверка Origin** для изменяющих запросов: свой origin — Host, X-Forwarded-Host (прокси Next.js его ставит) или PUBLIC_URL; запросы без Origin (не браузер) пропускаются.
- **D-089. Ячейки Excel с переносом строки** — в одну строку через « / » (иначе продолжение терялось при переиндексации); CSV читается потоком (поля в кавычках с переносами); TXT/CSV — не больше 50 МБ с предупреждением.
- **D-090. uvicorn `--timeout-keep-alive 75`:** при 5 с по умолчанию сервер закрывал соединение в момент, когда прокси Next.js отправлял в него запрос (ECONNRESET у пользователя). Лимиты частоты отключаемы (`RATE_LIMITS_ENABLED`), в dev-стеке выключены: e2e регистрирует десятки организаций с одного адреса.
